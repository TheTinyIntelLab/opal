## 2. Implement and train three models with a shared contract

Build `Opal-Base`, `Opal-Interaction` and `Opal-Guard` as a coherent series. These are functional variants, not arbitrary small/large labels or three renamed copies of the same model. All predict an aggregate expression-change vector from measured single-perturbation profiles, with declared context and intervention identities. The first release supports observed singles; do not advertise unseen-single or dose/state extrapolation.

**Opal-Base:** implement the fitted reference expert. Start from observed-single additivity and learn a regularized correction from development pair labels. Reuse the existing shared, global, single-profile and component-additive reference implementations rather than inventing another baseline grid. Select the reference configuration inside development folds, store its actual family and coefficients in the checkpoint, and make this a first-class trainable/predictable model. Preserve zero correction for unsupported identity components. This model is the dependable comparison and potential default, not a requirement that every series member be neural.

**Opal-Interaction:** add a genuinely trainable, compact nonlinear residual model on top of a frozen fitted Base expert. For single profiles `s_a` and `s_b`, use a shared small encoder `h`, a symmetric interaction feature `h(s_a) * h(s_b)`, and a learned output projection. Predict `Base(s_a,s_b) + W[h(s_a) * h(s_b)]`. Begin with a two-layer encoder of hidden width 64 and interaction width 16, training-only input scaling, and an output dimension equal to the frozen gene endpoint. Learn from development residuals with weighted MSE and regularization. Symmetry must hold in preprocessing, reference prediction and the interaction branch. Do not train an unbounded generative foundation model on a few hundred aggregate pair labels.

**Opal-Guard:** learn when to use the interaction branch. Predict `Base + gate(query_support) * (Interaction - Base)`, where the scalar gate lies in `[0,1]`. Train a small regularized gate using grouped out-of-fold Base/Interaction predictions from development pairs; fitting the gate on in-sample base-model predictions is not sufficient. Gate inputs may include development-graph component degrees, distance from allowed query singles to training singles, and declared source-context support. They must not include query-pair outcomes, outcome-derived query clusters or evaluator scores. Fit gate transforms within development cross-fitting. Missing essential assay/reference inputs cause a refusal; unsupported interaction support causes a documented Base fallback. The gate is a learned mixture weight, not calibrated uncertainty, and its prediction quality must be measured rather than assumed.

Before new fitting, freeze the architecture, optimization settings, comparison budget and compute limits in a configuration. Use a small bounded regularization menu, fixed training seeds and a finite epoch cap with development-only early stopping; do not keep trying widths, encoders or seeds until something wins. Match the data-access contract for all three variants and disclose unequal optimization budgets. Preserve every attempt, failure and negative result. Include ablations for the interaction branch and learned gate so the series has an assessable reason for its added complexity.

Provide a common `fit`, `predict`, `save` and `load` interface, a model registry, and CLI commands for training, evaluation and batch prediction using existing `opal` conventions. Checkpoints must contain learned parameters, architecture, feature/gene order, assay units, source and split lineage, fitted transforms, seed/version and integrity hashes.
